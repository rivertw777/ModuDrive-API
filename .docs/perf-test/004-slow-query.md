# 느린 쿼리 격리 테스트

느린 쿼리가 커넥션 풀을 다 차지해 다른 사용자의 요청까지 막는지, 그리고 시간 제한·벌크헤드([006 2-5](../spec/006-resilience-spec.md#2-5-db-쿼리))로 막히지 않게 되는지 확인한 테스트다. 같은 데이터로 느린 쿼리를 찾는 과정(식별)도 같이 했다.

## 1. 테스트 시나리오

| 시나리오 | 하는 일 | 확인할 것 |
|---|---|---|
| 식별 | 파일 100만 개 드라이브에서 file-service의 조회 API를 3번씩 호출한 뒤 `pg_stat_statements` 상위 문장을 본다 | API별 응답·시간, 시간을 가장 많이 쓴 문장 |
| 격리 | 같은 드라이브에서 검색 20개를 60초 동안 쉬지 않고 보내면서, 다른 사용자(파일 100개)의 폴더 목록을 1초마다 60번 호출 | 폴더 목록 응답 시간·상태, 커넥션 풀 대기 수, 성공한 검색 수 |
| 큰 폴더 | 하위 10만 개 폴더의 이동·휴지통·복원·영구 삭제 (002 `cascade.py`) | 시간 제한에 걸려 끊기는 문장이 없는지 |
| 큰 폴더 + commit | 하위 10만 개 폴더를 영구 삭제·이동하는 동안 같은 드라이브에 빈 파일 commit을 계속 보냄 (002 `contend.py`) | 영구 삭제·이동이 끝나는지, commit이 잠금 대기 3초에 걸리는지 |

- 드라이브: 파일 이름은 `보고서_123456.pdf`처럼 단어 12개 × 번호 × 확장자 6개, 폴더 1,000개에 나눠 담는다.
- 검색어: `회의록_123` (94건 일치). 드라이브 전체를 읽지만 결과는 보통 검색만큼 작다.
- 격리 시나리오는 이미지 하나로, 설정(`SPRING_APPLICATION_JSON`)만 바꿔 세 상태를 잰다. 상태마다 3회.

| 상태 | 시간 제한 | 검색 벌크헤드 |
|---|---|---|
| 끔 | 없음 (`statement_timeout=0` 등) | 사실상 없음 (자리 1,000) |
| 시간 제한만 | 쿼리 5초 · 잠금 3초 | 사실상 없음 |
| 시간 제한 + 벌크헤드 | 쿼리 5초 · 잠금 3초 | 자리 3 (배포값), 5 |

- file-service를 compose 네트워크 안에서 `X_USER_ID` 헤더로 직접 호출한다. 풀 대기 수는 file-service의 `/actuator/prometheus`(`hikaricp_connections_pending`)를 0.5초마다 읽는다.

레포 루트에서, 인프라가 떠 있는 상태로 실행한다.

```bash
.scripts/perf-test/scenario.sh up                         # 측정용 컨테이너
.scripts/perf-test/scenario.sh deploy slowq               # 작업 트리로 이미지 빌드
.scripts/perf-test/004-slow-query/run.sh off 3            # 상태마다 3회 (처음 실행 때 드라이브를 만든다)
.scripts/perf-test/004-slow-query/run.sh timeout 3
.scripts/perf-test/004-slow-query/run.sh bulkhead 3
SEATS=5 .scripts/perf-test/004-slow-query/run.sh bulkhead 3
.scripts/perf-test/004-slow-query/run.sh bulkhead 0       # 배포 설정으로 되돌림
docker exec -e PYTHONPATH=/w bench sh -c "cd /w/004-slow-query && python identify.py <label>"
ROUNDS=1 SKIP_WAIT=1 .scripts/perf-test/scenario.sh cascade <label> 100000
ROUNDS=1 .scripts/perf-test/scenario.sh contend <label> 100000
.scripts/perf-test/scenario.sh cleanup                    # 측정용 드라이브 삭제
```

스크립트와 결과 원본(json)은 `.scripts/perf-test/004-slow-query/`에 있다.

## 2. 테스트 결과

2026-11-18, 로컬 compose.

### 2-1. 식별

| API | 응답 | 시간 (중앙값) |
|---|---|---|
| 검색 — 드문 이름 (94건) | 200 | 161ms |
| 검색 — 흔한 단어 (`회의록`, 약 8만 3천 건) | 500 | 649ms |
| 전체 파일 | 500 | 8,483ms |
| 카테고리 (이미지) | 500 | 4,562ms |
| 폴더 목록 (1,000개 든 폴더) | 200 | 22ms |
| 최근 문서함 · 휴지통 · 사용량 | 200 | 7~10ms |

| 문장 | 호출 | 평균 | 호출당 행 |
|---|---|---|---|
| 드라이브의 파일 전부 (`namespace_id = ? and directory = false`) — 전체 파일 · 카테고리 | 8 | 1,256.8ms | 1,000,000 |
| 검색 (`upper(name) like upper('%…%')`) | 8 | 170.1ms | 41,713 |

- 500 세 개는 모두 같은 원인이다. 결과 행을 전부 읽은 뒤 즐겨찾기 여부를 `file_id in (…)` 한 문장으로 조회하는데, 행이 65,535개를 넘으면 Postgres 바인드 파라미터 한도에 걸린다.
- 카테고리는 드라이브의 파일을 전부 읽고 확장자로 거르는 일을 애플리케이션에서 한다.
- 검색은 `namespace_id` 인덱스로 드라이브의 행을 전부 가져온 뒤 이름 조건으로 거른다(`auto_explain`: Bitmap Index Scan → Filter).

### 2-2. 격리

칸 값은 3회의 값(괄호는 3회 중앙값). 부하가 없을 때 폴더 목록은 6~24ms, 검색 하나는 141~315ms.

| 상태 | 폴더 목록 중앙값 | 폴더 목록 최대 | 풀 대기 최대 | 성공한 검색 (60초) |
|---|---|---|---|---|
| 끔 | 1,236 / 762 / 768ms (768) | 2,900 / 1,109 / 1,516ms | 13 / 13 / 12 | 554 / 854 / 854 |
| 시간 제한만 | 754 / 737 / 753ms (753) | 1,207 / 1,558 / 1,262ms | 12 / 12 / 12 | 848 / 864 / 863 |
| 시간 제한 + 벌크헤드 (자리 3) | 42 / 32 / 28ms (32) | 146 / 78 / 70ms | 0 / 0 / 0 | 389 / 396 / 393 |
| 시간 제한 + 벌크헤드 (자리 5) | 36 / 31 / 30ms (31) | 136 / 63 / 66ms | 0 / 0 / 0 | 434 / 432 / 434 |

- 폴더 목록 60번은 모든 상태에서 모두 200이었다. 끔·시간 제한만 상태의 지연은 커넥션 대기(Hikari 3초 제한 안쪽)다.
- 시간 제한만으로는 달라지지 않았다. 이 상태에서 가장 긴 검색 요청도 2.5~2.9초(커넥션 대기 포함)로 5초에 못 미쳐, 끊긴 문장 없이 검색이 모두 200이었다.
- 벌크헤드 상태에서 자리를 못 받은 검색은 503(`SEARCH_UNAVAILABLE`)으로 바로 거절됐다(60초에 약 6만 번 — 스크립트가 기다리지 않고 다시 보낸다).
- 자리 5는 자리 3보다 성공한 검색이 약 10% 많고 폴더 목록은 같았다. 검색 최대 지연은 0.6초에서 1.7~1.8초로 늘었다. 자리 3을 배포값으로 둔다.

### 2-3. 큰 폴더

하위 10만 개, 1회, 혼자 실행. 칸 값은 `SQL 수 / 응답 시간`.

| 이동 | 휴지통 | 복원 | 영구 삭제 |
|---|---|---|---|
| 6 / 1,986ms | 4 / 1,256~1,369ms | 5 / 1,571ms | 18 / 8,426ms |

- 혼자 실행할 때는 끊긴 문장이 없었다. 문장마다 5초 아래다.

### 2-4. 큰 폴더 + commit

하위 10만 개, 1회. commit은 응답 안의 파일별 결과로 센다.

| 상태 | 영구 삭제 | 그동안 드라이브 루트 commit | 이동 | 그동안 그 폴더 안 commit |
|---|---|---|---|---|
| 끔 | 10,134ms 성공 | 451건 모두 성공, 최대 197ms | 1,258ms 성공 | 10건 모두 성공, 최대 1,258ms |
| 시간 제한 (연쇄 작업도 5초) | 503 — 블록 참조 해제 문장이 5초에 끊김 | — | — | — |
| 시간 제한 (연쇄 작업은 60초) | 10,258ms 성공 | 453건 모두 성공, 최대 212ms | 1,324ms 성공 | 10건 모두 성공, 최대 1,321ms |

- 혼자서는 5초 안에 끝나던 블록 참조 해제(30만 행)가, commit과 함께 돌자 5초를 넘었다. 연쇄 작업은 그 트랜잭션에서만 제한을 60초로 늘린다([006 2-5-1](../spec/006-resilience-spec.md#2-5-1-시간-제한)).
- commit은 잠금 대기 3초에 걸린 것이 없었다(가장 오래 기다린 commit 1.3초).
