# 공유 폴더 권한 계산 성능 테스트

공유받은 폴더 안 깊은 곳의 파일을 열거나 목록으로 볼 때, 폴더 깊이에 따라 SQL 수와 응답 시간이 어떻게 변하는지 확인한 테스트다. 폴더 공유는 상속되므로, 권한은 확인할 때마다 위쪽 폴더를 거슬러 올라가며 계산한다(`.docs/spec/003-file-sharing-spec.md`).

## 1. 테스트 시나리오

1. 소유자가 깊이 d의 폴더 사슬 `/p0/p1/…/p{d-1}`을 만들고, 맨 아래에 파일 50개를 둔다.
2. 맨 위 `/p0`만 다른 사용자에게 VIEWER로 공유한다. 그 아래는 전부 상속이다.
3. 공유받은 사람이 그 50개를 즐겨찾기하고, 최근에 연 기록을 남긴다.
4. 아래 API를 공유받은 사람의 `X_USER_ID`로 200회씩 호출한다.

| API | 권한 계산이 일어나는 곳 |
|---|---|
| 파일 상세 `GET /api/v1/files/{id}` | 권한 확인, 그리고 "공유한 사용자/날짜"와 응답의 내 권한 |
| 공유 폴더 목록 `GET /api/v1/files/{id}/children` (자식 50개) | 폴더 권한, 그리고 자식마다 직접 받은 공유 |
| 즐겨찾기 `GET /api/v1/files/favorites` (50개) | 파일마다 권한 다시 확인 |
| 최근 문서함 `GET /api/v1/files/recent?limit=50` | 파일마다 권한 다시 확인 |

레포 루트에서, 인프라와 서비스가 떠 있는 상태로 실행한다.

```bash
.scripts/perf-test/scenario.sh up
.scripts/perf-test/scenario.sh deploy asis       # 비교 기준 코드
.scripts/perf-test/scenario.sh perm asis         # 깊이 1, 5, 10, 20
.scripts/perf-test/scenario.sh deploy tobe       # 개선 코드
.scripts/perf-test/scenario.sh perm tobe
.scripts/perf-test/scenario.sh cleanup
.scripts/perf-test/scenario.sh down
```

스크립트는 `.scripts/perf-test/002-share-permission/perm.py`, 결과 원본은 그 아래 `results/`에 있다.

## 2. 테스트 결과

2026-10-11. 개선 전은 `dev`(65bfe24)로, 조상 폴더를 경로 한 칸마다 조회하고 공유를 조상마다 조회했다. 그리고 한 요청 안에서 같은 계산을 여러 번 했다. 개선 후는 조상 1회와 공유 1회로 판정하고, 그 결과를 요청 안에서 재사용한다. 칸 값은 `SQL 수 / p50`이다.

| API | 깊이 1 | 깊이 5 | 깊이 10 | 깊이 20 |
|---|---|---|---|---|
| 파일 상세 개선 전 | 14 / 25ms | 38 / 39ms | 68 / 55ms | 128 / 96ms |
| 파일 상세 개선 후 | 7 / 29ms | 7 / 22ms | 7 / 21ms | 7 / 21ms |
| 공유 폴더 목록 개선 전 | 56 / 41ms | 80 / 54ms | 110 / 71ms | 170 / 109ms |
| 공유 폴더 목록 개선 후 | 5 / 22ms | 6 / 20ms | 6 / 18ms | 6 / 18ms |
| 즐겨찾기 개선 전 | 202 / 127ms | 602 / 357ms | 1,102 / 668ms | 2,102 / 1.26s |
| 즐겨찾기 개선 후 | 152 / 149ms | 152 / 140ms | 152 / 145ms | 152 / 151ms |
| 최근 문서함 개선 전 | 353 / 213ms | 1,153 / 671ms | 2,153 / 1.30s | 4,153 / 2.45s |
| 최근 문서함 개선 후 | 153 / 131ms | 153 / 134ms | 153 / 145ms | 153 / 150ms |

- 개선 전에는 SQL 수가 깊이에 비례했다. 권한 확인 한 번에 `2 × 깊이 + 1`회였고, 파일 상세는 그걸 3번 반복했다. 개선 후에는 깊이와 상관없이 고정이다.
- 깊이 1에서는 이득이 없다. 파일 상세와 즐겨찾기는 p50이 4~22ms 높게 나왔는데, 측정 편차 범위 안이다.
- 한계: 즐겨찾기와 최근 문서함은 아직 파일마다 조회(`findById` 1회 + 권한 2회)해서 50개에 SQL 약 150회가 나간다. 깊이에 곱해지던 부분만 없앴다.
