# 파일 업로드 성능 테스트

브라우저(Chromium)에서 WEB으로 실제 사용자처럼 파일을 올리면서([001 2](../spec/001-file-upload-spec.md#2-파일-업로드)) 걸린 시간과 DB·Redis 호출 수를 잰 테스트다. 큰 파일, 작은 파일, 여러 종류가 섞인 폴더를 혼자 올릴 때와 10명이 동시에 올릴 때로 나눠 잰다. 업로드 최적화를 성격별로 네 단계로 묶어, 최적화 전과 각 단계를 같은 조건으로 비교한다([2](#2-최적화-단계)). 마지막에는 배포한 서비스를 구글 드라이브·네이버 MYBOX와 같은 파일로 비교한다.

## 1. 테스트 시나리오

| # | 시나리오 | 하는 일 |
|---|---|---|
| 1 | 큰 파일 | 5GiB 파일 1개 (4MiB 블록 1,280개 — 한 파일의 최대) |
| 2 | 작은 파일 | 10KiB 파일 1,000개 (파일마다 블록 1개, commit은 100개씩 10번) |
| 3 | 혼합 폴더 | 업무 폴더 하나 (파일 552개, 1.31GiB) — 아래 표 |
| 4 | 동시 · 큰 파일 | 10명이 동시에 각자 1 |
| 5 | 동시 · 작은 파일 | 10명이 동시에 각자 2 |
| 6 | 동시 · 혼합 폴더 | 10명이 동시에 각자 3 |

혼합 폴더는 종류마다 실제에 가까운 크기로, 하위 폴더 깊이를 섞었다. 크기는 범위 안에서 고정된 시드로 고르게 뽑아 블록은 786개다. 확장자는 이름에만 쓰이고(`FileCategory`) 업로드 비용은 크기와 폴더 구조로 정해진다.

| 하위 폴더 | 종류 | 파일 수 | 크기 |
|---|---|---|---|
| `문서` | pdf / docx | 60 / 50 | 100KiB~5MiB / 20KiB~2MiB |
| `문서/보고서` | xlsx / hwp | 40 / 20 | 10KiB~1MiB / 30KiB~3MiB |
| `코드/src/main` | java | 250 | 1~20KiB |
| `코드` | json | 30 | 1~50KiB |
| `사진` | jpg | 60 | 2~6MiB |
| `사진/스크린샷` | png | 20 | 100KiB~3MiB |
| `음악` | mp3 | 15 | 3~10MiB |
| `압축` | zip | 5 | 10~60MiB |
| `영상` | mp4 | 2 | 120MiB, 400MiB |

한 라운드는 실제 사용자가 하는 그대로다.

1. 새 회원이 가입하고 로그인한다. 가입·로그인 API는 WEB 페이지 안에서 부르고, 메일 인증 코드(가입, 새 기기 로그인)는 Mailpit에서 읽는다. 드라이브는 가입 이벤트로 file-service가 만든다(기본 한도 20GiB).
2. 드라이브 화면에서 `업로드` → `파일 업로드`(1·2) 또는 `폴더 업로드`(3)를 눌러 파일 선택 창에서 고른다.
3. 업로드 상태 창이 `N개 항목 업로드 완료`가 될 때까지 기다린다. 파일을 고른 순간부터 이때까지가 전체 시간이다. 실패가 하나라도 있으면(`N개 완료, M개 실패`) 그 라운드는 실패다.
4. 로그아웃하고, 그 회원·드라이브·DB 행·S3 블록을 지운다.

해시 계산, 이름 충돌 확인(`POST /api/v1/files/batch`), 묶음 나누기, URL 요청, S3 PUT, 재시도, CORS preflight가 모두 WEB 코드와 브라우저가 하는 그대로 일어나고, API 요청은 전부 gateway(세션 확인, CSRF 검사)를 거친다. 함께 재는 값은 다음과 같다.

| 값 | 재는 법 |
|---|---|
| 요청 종류별 수·실패 수·p50, 처음 시작과 마지막 끝 시각 | 브라우저 네트워크 기록. 종류는 batch, commit1(`needBlocks`가 남은 commit), urls(업로드 URL 요청), put(S3 PUT), commit2(버전을 만든 commit), other |
| DB 쿼리 수 | file_db의 pg_stat_statements (라운드 시작 전에 비움) |
| Redis 왕복 수 | `INFO commandstats`의 차이. `upload-count.lua`가 안에서 실행하는 `INCR`·`PEXPIRE`는 왕복이 아니라 빼고 센다 |

- 서비스를 띄운 뒤 워밍업 1번(시나리오 2), 시나리오마다 3라운드, 표는 중앙값이다.
- 동시 업로드는 10명이 브라우저 컨텍스트 10개(쿠키·연결 따로)에서 같이 시작한다. DB·Redis 수는 10명 합계이고, 시간은 사람마다 잰 값의 중앙값과 가장 늦은 사람(max)이다.
- 파일은 디스크에 한 벌 만들어 모든 라운드·회원이 같이 쓴다. 블록은 회원마다 따로 저장되므로(`blocks/<회원>/`) 새 회원은 같은 파일도 전부 다시 올린다.
- `TIMELINE=1`이면 요청마다의 시작·끝 시각을 CORS preflight까지 DevTools 프로토콜로 받아 `results/<label>.timeline.jsonl`에 남긴다(Playwright 이벤트에는 preflight가 없다).

### 측정 환경

| 항목 | 값 |
|---|---|
| PC | Intel i5-14500HX, WSL2(`.wslconfig` 프로세서 12개, 메모리 16GB, 스왑 8GB), Docker 29.9.2 |
| 컨테이너 자원 | compose에 CPU·메모리 제한 없음 — 모든 컨테이너가 위 12코어·16GB를 나눠 쓴다 |
| 인프라 | `postgres:18-alpine`(설정 기본값 + `pg_stat_statements`), `redis:7-alpine`, `localstack/localstack:2026.08.3` |
| JVM | `eclipse-temurin:25-jre-alpine`, `-XX:+UseCompactObjectHeaders`, AOT 캐시 없음(로컬 이미지), GC·힙은 JVM 기본(코어가 2개 넘어 G1, 힙 최대는 메모리의 1/4) |
| 프로필 | `dev` — trace 샘플링 100%, JDBC 쿼리마다 span. SQL 출력(`show_sql`·`format_sql`·`use_sql_comments`)은 `run.sh deploy`가 `no-sql-log.yml`로 끈다 |
| 요청 처리 | Tomcat 가상 스레드, Hikari 풀 10개(기본값), 연결 대기 3초 |
| Hibernate | `jdbc.batch_size` 50, `order_inserts`, `reWriteBatchedInserts` 꺼짐 |
| file → storage | Feign 읽기 시간 제한 30초 |
| storage → S3 | 블록 확인 동시 8개(`LOOKUP_PARALLELISM`), 해시 64개 이상이면 목록 조회(`LIST_MIN_HASHES`), `s3Lookup` 벌크헤드 40자리·최대 1초 대기, S3 연결 풀 85개, SDK 시도 2번 |
| 업로드 단위 | 블록 4MiB, URL 요청 하나에 64개, 사용자당 24시간에 블록 25,600개 |
| WEB | `vite preview`로 띄운 빌드본(`VITE_API_BASE_URL=http://localhost:10001`), 포트 3000(`CLIENT_URL`) |
| 브라우저 | Chromium 153 (Playwright 1.63.0, `channel: chromium` — 새 headless), 기본 설정 |

실제 사용자와 다른 점은 다음과 같다.

- 가입·로그인은 화면 대신 WEB 페이지 안에서 API를 부른다. 업로드 시간에는 들어가지 않는다.
- 동시 업로드의 10명은 한 PC에서 브라우저 하나를 나눠 쓴다. 해시 계산에 쓰는 CPU도 10명이 나눠 쓴다.

레포 루트에서, 인프라와 서비스가 떠 있는 상태로 실행한다.

```bash
.scripts/perf-test/scenario.sh up                              # pg_stat_statements 켜기
cd .scripts/perf-test/001-upload/web && npm ci && cd -         # Playwright
node .scripts/perf-test/001-upload/web/upload-web.mjs files    # 시나리오 파일 (~/upload-bench-files, 약 6.3GiB)
.scripts/perf-test/001-upload/run.sh image blog-c897           # 작업 트리로 file·storage-service 이미지를 만들어 blog-c897로 태그
.scripts/perf-test/001-upload/web/measure.sh c897:web2         # 상태마다: deploy → WEB 빌드 띄우기 → 워밍업 → 시나리오 1~6 × 3라운드
node .scripts/perf-test/001-upload/web/upload-web.mjs rm-files # 시나리오 파일 삭제
```

`measure.sh`가 부르는 한 시나리오는 `upload-web.mjs <label> <라운드> <big|small|mixed> [사람 수]`다. 스크립트는 `.scripts/perf-test/001-upload/web/`, 결과 원본(라운드마다 JSON 한 줄)은 `.scripts/perf-test/001-upload/results/`에 있다.

## 2. 최적화 단계

업로드 최적화 PR을 성격에 따라 네 단계로 묶고, 최적화 전까지 다섯 상태를 잰다.

| 단계 | 상태 | PR | 바꾼 것 |
|---|---|---|---|
| 최적화 전 | `base` | – | – |
| 1. 호출 묶기 | `c684` | #682, #684 | URL 요청의 Redis 호출을 블록마다 하던 것에서 요청당 17번 이하로 묶는다. 1차 commit 사전 검사를 파일마다 쿼리 2번에서 묶음당 1번 + 폴더당 1번으로 묶는다. HEAD 동시 요청은 #682에서 8→32개로 늘렸다가 #684에서 8개로 되돌려 그대로다 |
| 2. 2차 commit 묶기 | `c693` | #687, #689, #691, #693, WEB #309 | 2차 commit을 묶음 하나에 트랜잭션 하나로(실패하면 파일별로) 한다. 블록 확인은 해시 64개 이상이면 HEAD 대신 S3 목록 조회로 한다. 버전 블록 해제·이름 조회·조상 폴더 잠금을 묶음 단위로 한다. 폴더 생성은 `insert … on conflict do nothing`으로 한다. WEB은 묶음 2개를 동시에 진행한다 |
| 3. UPDATE 묶기 | `c897` | #897 | 묶음 안에서 파일마다 하던 버전 UPDATE를 `unnest` UPDATE 한 문장으로 한다 |
| 4. 진행률 렌더 묶기 | `c897w325` | WEB #325 | 블록 해시·PUT마다 업로드 상태 창 전체를 다시 그리던 것을, 바이트 진행은 100ms에 한 번 반영하고 행은 `React.memo`로 바뀐 것만 다시 그린다. 서버는 `c897`과 같다 |

상태는 최신 dev(`cc3dc0bb`)에서 PR의 merge 커밋을 최근 것부터 `git revert -m 1`로 되돌려 만든다.

| 상태 | 만드는 법 |
|---|---|
| `c897w325` | `c897`과 같은 서버, WEB만 #325(`fa39fca`)까지 |
| `c897` | `cc3dc0bb` 그대로 |
| `c693` | `c897`에서 #897(`c2debce2`)을 되돌린다 |
| `c684` | `c693`에서 #693(`b9640911`), #691(`e41c85ce`), #689(`826bbee0`), #687(`66b6e974`)을 되돌린다 |
| `base` | `c684`에서 #684(`18f248bb`), #682(`ac5490e2`)를 되돌린다 |

- 상태끼리 다른 것은 file·storage-service의 업로드 코드뿐이다. 되돌린 PR에 같이 들어 있던 설정(S3 연결 풀 85개, file → storage Feign 읽기 시간 제한 30초)은 되돌린 뒤 최신 값으로 다시 맞춘다. 다른 서비스·인프라·[측정 환경](#측정-환경)은 다섯 상태가 같다.
- WEB은 상태에 맞는 빌드를 쓴다. `base`·`c684`는 #325 전 WEB(`2b561e5`)에서 #309(`43f92fa`, 묶음 2개 동시)를 되돌린 빌드(`web1`, 묶음 하나씩), `c693`·`c897`은 #325 전 WEB 그대로(`web2`), `c897w325`는 #325 머지(`fa39fca`) 빌드(`web3`)다. 모두 WEB의 worktree를 `.temp/web-bench/<web>/`에 두고 `VITE_API_BASE_URL=http://localhost:10001 npm run build`로 빌드한다. 커밋하지 않은 WEB 변경은 넣지 않는다.
- 상태마다 `run.sh image blog-<상태>`로 이미지를 만들어 두고, 같은 날 `measure.sh base:web1 c684:web1 c693:web2 c897:web2`로 연달아 잰다. 4단계는 서버가 3단계와 같아, `c897` 이미지 하나로 띄워 두고 `alternate.sh web2 web3`로 두 WEB 빌드를 라운드마다 번갈아 잰다(시나리오 1·2·3·5, 라운드마다 먼저 재는 쪽을 바꾼다).
- 상태를 바꿀 때마다 측정용 회원·드라이브·DB 행·S3 블록을 모두 지우고 시작한다.
- 1단계에서 HEAD 동시 요청을 8개로 되돌린 이유: 로컬 10명 동시 업로드에서 32개가 S3 호출 자리(40개, 최대 1초 대기)를 기다리다 503 → 재시도로 오히려 느려졌다(16.8 → 24.4초). AWS S3에서 재 보니 HEAD가 p50 14ms라 8개로도 자리 거절이 없었고(5GiB commit 10개 동시 약 17초), 32개가 빠른 경우는 5GiB 혼자 2.3 → 1.8초뿐이었다(2026-10-18, `s3-head.py`, `results/aws-s3-head.json`). 지금은 해시가 64개 미만인 commit만 HEAD를 쓴다.

- put은 같은 PC 안에서 LocalStack으로 보낸 시간이라, 브라우저에서 S3로 올리는 실제 시간과 다르다([4](#4-배포구글-드라이브네이버-mybox-비교)).
- 4단계는 파일이 많을 때(2·5)만 빨라진다. 2의 요청 타임라인(라운드마다)에서 PUT이 하나도 없는 시간이 1.82\~2.50초에서 0.88\~1.06초로, PUT 구간이 6.4\~7.0초에서 4.6\~5.1초로 줄었다. 1·3은 3단계에서도 PUT이 하나도 없는 시간이 라운드마다 0.03초 이하라 줄일 렌더 대기가 없고, 시간은 약 2.1초 걸린 PUT 수가 정한다(1의 3단계: 0번인 라운드 18.1초, 43번인 라운드 40.1초).
- 4단계 측정의 1라운드는 서비스를 띄운 직후라 storage-service의 미커밋 블록 정리([001 2-4-1](../spec/001-file-upload-spec.md#2-4-1-저장-순서))가 전날 측정분을 처리하는 시간과 겹쳐, 두 단계 모두 DB 쿼리·Redis 왕복이 늘고(1에서 DB 약 2,030) 시간도 가장 길었다. 2·3라운드는 두 단계의 DB 쿼리·Redis 왕복이 같다.

## 4. 배포·구글 드라이브·네이버 MYBOX 비교

2026-11-12 10시(1회차), 10시 37분(2회차), 11시 29분(3회차)에 유선 랜에 연결한 같은 PC의 Chrome으로 회차마다 서비스별로 한 번씩 올렸다(결과 원본 `results/web-compare-1112.json`). 회선 업로드 속도는 speedtest로 473Mbps다(2회차와 3회차 사이에 두 번 잼).

- 배포한 서비스는 demo(서울 리전, gateway·auth·file·storage 1 vCPU / 2GB, WEB은 4단계까지)다. 재기 전에 작은 파일 1,000개와 하위 폴더가 있는 작은 폴더를 한 번씩 올려 워밍업했다.
- 바탕화면 `업로드-테스트`의 `작은 파일`·`큰 파일`·`혼합 폴더`를 모두 폴더 업로드로 올렸다. 혼합 폴더는 3과 하위 폴더·파일 수가 같고, 크기 합은 1.29GiB다. 회차마다 재기 전에 `python3 .scripts/perf-test/001-upload/refresh-files.py <업로드-테스트 경로>`로 내용을 새로 썼다(배포한 서비스는 같은 블록을 다시 올리지 않는다).
- 1·2회차는 시나리오마다 ModuDrive → 구글 드라이브 → MYBOX 순서로, 3회차는 그 반대 순서로 이어서 올렸다.
- 시간은 화면 녹화(30fps)에서 쟀다. 시작은 브라우저의 업로드 확인 창이 닫힌 프레임, 끝은 업로드 창에 완료가 표시된 첫 프레임이다.
- 평균은 세 회차의 중앙값에서 20% 넘게 벗어난 값을 빼고 냈다. 빠진 값은 구글 드라이브 2의 3회차(175.0초) 하나다.

## 5. 측정의 한계

- LocalStack은 AWS S3와 지연 특성이 다르다.
- LocalStack은 4MiB 블록 PUT 하나에 약 2.1초가 걸리는 경우가 있고, 블록이 크고 많을수록, 측정 시간대에 따라 횟수가 크게 다르다. 요청마다의 시간은 `TIMELINE=1`로 남겨 라운드마다 확인한다.
- 같은 이미지라도 측정한 날·서비스를 다시 띄운 직후인지에 따라 절대 시간이 달랐다. 전후 비교는 같은 날 연달아 잰 값끼리만 한다.
