# 파일 업로드 성능 테스트

demo에 배포한 서비스에 PC의 Chrome으로 WEB에서 실제 사용자처럼 파일을 올리면서([001 2](../spec/001-file-upload-spec.md#2-파일-업로드)) 걸린 시간을 잰 테스트다. 큰 파일, 작은 파일, 여러 종류가 섞인 폴더를 혼자 올린다. 업로드 최적화를 성격별로 세 단계로 묶어, 최적화 전과 각 단계를 차례로 demo에 배포해 쟀다([2](#2-최적화-단계)). 마지막에는 배포한 서비스를 구글 드라이브·네이버 MYBOX와 같은 파일로 비교한다.

## 1. 테스트 시나리오

| # | 시나리오 | 하는 일 |
|---|---|---|
| 1 | 큰 파일 | 5GiB 파일 1개 (4MiB 블록 1,280개 — 한 파일의 최대) |
| 2 | 작은 파일 | 10KiB 파일 1,000개 (파일마다 블록 1개, commit은 100개씩 10번) |
| 3 | 혼합 폴더 | 업무 폴더 하나 (파일 552개, 1.29GiB) — 아래 표 |

혼합 폴더는 종류마다 실제에 가까운 크기로, 하위 폴더 깊이를 섞었다. 확장자는 이름에만 쓰이고(`FileCategory`) 업로드 비용은 크기와 폴더 구조로 정해진다.

| 하위 폴더 | 종류 | 파일 수 | 크기 |
|---|---|---|---|
| `문서` | pdf / docx | 60 / 50 | 100KiB~5MiB / 20KiB~2MiB |
| `문서/보고서` | xlsx / hwp | 40 / 20 | 10KiB~1MiB / 30KiB~3MiB |
| `코드/src/main` | java | 250 | 1~20KiB |
| `코드` | json | 30 | 1~50KiB |
| `사진` | jpg | 60 | 2~6MiB |
| `사진/스크린샷` | png | 20 | 100KiB~3MiB |
| `음악` | mp3 | 15 | 3~10MiB |
| `압축` | zip | 5 | 10~60MiB |
| `영상` | mp4 | 2 | 120MiB, 400MiB |

### 측정 환경

| 항목 | 값 |
|---|---|
| 서버 | demo — AWS 서울 리전, ECS Fargate 서비스마다 태스크 1개, gateway·auth·file·storage 1 vCPU / 2GB |
| DB · Redis | RDS PostgreSQL 18 (db.t4g.micro), ElastiCache Valkey 8.1 (cache.t4g.micro) |
| 블록 저장 · WEB | S3, WEB은 S3 + CloudFront |
| 클라이언트 | Intel i5-14500HX, 메모리 32GB, Windows 11, 유선 랜(업로드 473Mbps), Chrome |

### 측정 방법

- 바탕화면 `업로드-테스트`의 `큰 파일`·`작은 파일`·`혼합 폴더`를 Chrome에서 폴더 업로드로 올린다.
- 단계를 배포한 뒤 작은 파일 1,000개로 한 번 워밍업하고 잰다.
- 단계·시나리오마다 여러 번 올리고, 표는 평균이다. 올릴 때마다 그 전에 `python3 .scripts/perf-test/001-upload/refresh-files.py <업로드-테스트 경로>`로 내용을 새로 쓴다(배포한 서비스는 같은 블록을 다시 올리지 않는다).
- 시간은 화면 녹화(30fps)에서 쟀다. 시작은 브라우저의 업로드 확인 창이 닫힌 프레임, 끝은 업로드 창의 상태 아이콘이 완료(✓)로 바뀐 첫 프레임이다.

## 2. 최적화 단계

업로드 최적화 PR을 성격에 따라 세 단계로 묶고, 최적화 전까지 네 상태를 잰다.

| 단계 | PR | 바꾼 것 |
|---|---|---|
| 처음 | – | – |
| 1. 호출 묶기 | #682, #684 | URL 요청의 Redis 호출을 블록마다 하던 것에서 요청당 17번 이하로 묶는다. 1차 commit 사전 검사를 파일마다 쿼리 2번에서 묶음당 1번 + 폴더당 1번으로 묶는다. HEAD 동시 요청은 #682에서 8→32개로 늘렸다가 #684에서 8개로 되돌려 그대로다 |
| 2. 2차 commit 묶기 | #687, #689, #897, #923 | 2차 commit을 묶음 하나에 트랜잭션 하나로(실패하면 파일별로) 한다. 블록 확인은 해시 512개 이상이면 HEAD 대신 S3 목록 조회로 한다(#687은 64개, #923에서 512개로). 버전 블록 해제·이름 조회·조상 폴더 잠금을 묶음 단위로 하고, 파일마다 하던 버전 UPDATE를 `unnest` UPDATE 한 문장으로 한다 |
| 3. 블록 전송 파이프라인 | WEB #328, #691, #693 | WEB이 묶음을 하나씩 차례로 하던 것을, 앞 묶음의 블록을 보내는 동안 다음 묶음의 commit·URL 요청을 진행하는 파이프라인(동시 묶음 최대 3개)으로 한다. 폴더 생성은 `insert … on conflict do nothing`으로 한다 |

상태는 dev(`bbd6d420`)에서 PR의 merge 커밋을 되돌려 만든 로컬 브랜치다.

| 상태 | 서버 | WEB |
|---|---|---|
| 처음 | `test/upload-stage0`(`84d644b9`) — #682\~#897을 모두 되돌림 | dev에서 #328을 되돌리고 동시 묶음 1개(묶음 하나씩) |
| 1단계 | `test/upload-stage1`(`1d3c48c1`) — #687\~#897을 되돌림 | 처음과 같음 |
| 2단계 | `test/upload-stage2`(`a4d7c127`) — #691, #693을 되돌림, `LIST_MIN_HASHES`만 512로(#923) | 처음과 같음 |
| 3단계 | dev(`746a9b05`, #923 포함) | dev |

- 상태끼리 다른 것은 file·storage-service의 업로드 코드와 WEB의 묶음 진행 방식뿐이다. 되돌린 PR에 같이 들어 있던 설정(S3 연결 풀 85개, file → storage Feign 읽기 시간 제한 30초)은 최신 값으로 다시 맞췄다. 업로드 상태 창 렌더(WEB #325)는 모든 상태에 들어 있다.
- 상태마다 file·storage 이미지를 로컬에서 빌드해 ECR에 올리고, demo의 작업 정의 이미지만 바꿔 배포했다. WEB 빌드도 상태마다 demo에 올렸다.
- 측정 중 사용자당 24시간 블록 한도(25,600개)를 넘지 않도록, 2·3단계는 storage-service의 한도를 임시로 올리고(`STORAGE_UPLOAD_BLOCKS_PER_WINDOW=1000000`) 쟀다.
- 측정이 끝난 뒤 demo는 측정 전 작업 정의로 되돌렸다.
- 1단계에서 HEAD 동시 요청을 8개로 되돌린 이유: 로컬 10명 동시 업로드에서 32개가 S3 호출 자리(40개, 최대 1초 대기)를 기다리다 503 → 재시도로 오히려 느려졌다(16.8 → 24.4초). AWS S3에서 재 보니 HEAD가 p50 14ms라 8개로도 자리 거절이 없었고(5GiB commit 10개 동시 약 17초), 32개가 빠른 경우는 5GiB 혼자 2.3 → 1.8초뿐이었다(2026-10-18, `s3-head.py`, `results/aws-s3-head.json`). 지금은 해시가 512개 미만인 commit만 HEAD를 쓴다.

## 4. 배포·구글 드라이브·네이버 MYBOX 비교

ModuDrive는 [3](#3-demo-결과)의 3단계 결과를 쓴다. 구글 드라이브·MYBOX는 2026-11-12 10시(1회차), 10시 37분(2회차), 11시 29분(3회차)에 유선 랜에 연결한 같은 PC의 Chrome으로 회차마다 한 번씩 올렸다(결과 원본 `results/web-compare-1112.json`). 회선 업로드 속도는 speedtest로 473Mbps다(2회차와 3회차 사이에 두 번 잼).

- 바탕화면 `업로드-테스트`의 `작은 파일`·`큰 파일`·`혼합 폴더`를 모두 폴더 업로드로 올렸다. 혼합 폴더는 3과 하위 폴더·파일 수가 같고, 크기 합은 1.29GiB다. 회차마다 재기 전에 `python3 .scripts/perf-test/001-upload/refresh-files.py <업로드-테스트 경로>`로 내용을 새로 썼다(배포한 서비스는 같은 블록을 다시 올리지 않는다).
- 1·2회차는 시나리오마다 구글 드라이브 → MYBOX 순서로, 3회차는 그 반대 순서로 이어서 올렸다.
- 시간은 화면 녹화(30fps)에서 쟀다. 시작은 브라우저의 업로드 확인 창이 닫힌 프레임, 끝은 업로드 창에 완료가 표시된 첫 프레임이다.
- 평균은 세 회차의 중앙값에서 20% 넘게 벗어난 값을 빼고 냈다. 빠진 값은 구글 드라이브 2의 3회차(175.0초) 하나다.

| # | 시나리오 (ModuDrive는 평균, 나머지는 1 / 2 / 3회차, 괄호는 평균) | ModuDrive | 구글 드라이브 | MYBOX |
|---|---|---|---|---|
| 1 | 5GiB 1개 | 97.9초 | 148.1 / 140.3 / 157.4 (148.6)초 | 183.8 / 161.2 / 151.6 (165.5)초 |
| 2 | 10KiB × 1,000개 | 9.7초 | 111.7 / 108.8 / 175.0 (110.2, 175.0 제외)초 | 51.5 / 51.0 / 52.3 (51.6)초 |
| 3 | 혼합 폴더 | 26.9초 | 422.1 / 411.9 / 426.5 (420.2)초 | 43.4 / 48.6 / 51.3 (47.8)초 |

- 회차마다 한 번씩 쟀으므로 그때의 네트워크 상태가 그대로 들어 있다.
